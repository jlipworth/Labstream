    Release and App Store status¶

    This page is the public source of truth for Labstream's distribution status and the release checks that can safely live in the repository. It does not contain signing identities, App Store Connect contact details, review credentials, tokens, private server addresses, or other secrets. Statements about processed builds and App Store Connect are repository records, not a live account query; verify them in App Store Connect again before any upload or submission.

    Product record and version numbers¶

    The four targets share the neutral org.labstream.Labstream bundle identifier and are intended for one App Store Connect universal-purchase record. The earlier private visionOS 1.6.0 build used a retired personal-namespace identifier; it is not the publication record for 1.6.1 and cannot be migrated because Apple freezes a record's bundle identifier after its first build upload.

    The publication topology is one product record with four platform versions and four binary archives: the LabstreamMobile iOS archive covers both iPhone and iPad, while visionOS, tvOS, and macOS each use their own archive. Metadata, screenshots, build selection, review notes, and acceptance remain platform-specific even when the platforms share one purchase record. A platform must not be marked ready merely because another platform passed review.

    The earlier recorded App Store Connect state included the shared app information, free price schedule, a Data Not Collected privacy answer (since superseded; see the current audit below), platform descriptions, review contacts, build selections, manual-release settings, and one privacy-safe synthetic placeholder screenshot for each submitted device family. Those screenshots prove the capture and upload path, but they are not the intended public product-page set. In that recorded state, app availability was not enabled. Licensed demo media, final screenshot capture and review, demo review access, review notes, physical-platform acceptance, storefront scope, Digital Services Act status where applicable, and final submission remain open.

    1.8.0 is the current source marketing version (CFBundleShortVersionString). The number in parentheses is the App Store build number (CFBundleVersion). A new marketing version begins at build 1; each replacement upload for the same platform and marketing version must use a higher build number. The repository's bump-version skill owns the per-platform bump, tagging, and verification procedure.

    Coordinated publication sequence¶

    For a new coordinated archive set or the first public release, use this order. If the neutral App Store Connect record already exists, verify it and add the required platform version instead of creating a duplicate record:

    1. In the Apple Developer account, confirm the neutral App ID and required capabilities, then make an Apple Distribution signing identity and platform-appropriate App Store provisioning available to Xcode. Do not commit certificates, private keys, profiles, account identifiers, or exports.
    2. Create the new App Store Connect app for org.labstream.Labstream, then add the visionOS, iOS/iPadOS, tvOS, and macOS platform versions to that one universal-purchase record. Do not reuse the retired personal-identity visionOS record.
    3. From the exact public release commit, produce and locally validate one archive each for Labstream, LabstreamMobile, LabstreamTV, and LabstreamMac. Confirm identity, version, build, entitlements, minimum OS, architecture, and device family before upload.

    Use scripts/testflight-release.py for steps 3 and 4 (the testflight-deploy skill documents the flow). preflight checks clean published source, per-scheme version/build, App Store profiles, the Apple Distribution identity, and that the build number is not already uploaded. archive writes manual-distribution-signed archives to Xcode's Organizer folder, validate checks each archive plus the four-app privacy manifest comparison, and upload --yes uploads with an App Store Connect API key. distribute --group <internal group> --yes adds already-processed builds to an internal TestFlight group. Organizer remains the place to generate the aggregate privacy report. For an on-demand build to internal testers, ship --group <internal group> --yes runs the whole sequence with --build-number auto (the commit count of HEAD) and adds the processed builds to that group; a release candidate can then be one of those builds, selected for review rather than archived again. Successful ships prune local archives to the newest three uploaded sets plus any set attached to an App Store version (prune-archives dry-runs the same policy).

    The script exists because Xcode 27 xcodebuild cannot use an account signed in through Xcode Settings ▸ Apple Accounts (No Accounts), and tvOS automatic signing fails while the team has no registered Apple TV. It therefore signs manually and scopes the profile to the app target, because Swift package targets reject a global PROVISIONING_PROFILE_SPECIFIER.

    The API key lives in 1Password and is read through a read-only service account whose token is kept in the login Keychain; local references stay in the gitignored scripts/asc.local.env. The key is written only to a private temporary file for the duration of a command. Never commit or publish the key, its identifiers, the team ID, or the service-account token. 4. Upload each archive and wait for App Store Connect processing. Treat warnings or missing platform associations as blockers; do not advance a different binary merely because it shares the version number. scripts/testflight-release.py status --wait reports processing, TestFlight state, and beta groups. A new platform version can inherit the previous version's build; select-build shows which versions still point at an older build and --yes attaches the new one. It never submits for review. 5. Establish the reviewer environment and its licensed sample-media inventory, then capture and privacy-review the final platform-specific screenshot sets. Complete shared app information plus platform metadata, build selection, privacy/export answers, review notes, and review access. Product-page text and review notes live in appstore/metadata/ and are edited by pull request; scripts/asc-metadata.py diff compares them with App Store Connect and push --yes writes the reviewed text. Review contact details, demo credentials, and the review server address stay only in App Store Connect. 6. Install processed builds through TestFlight on every submitted device family, starting from a fresh install for the identity boundary and sign-in checks. Record the platform-specific gates below. 7. Add only accepted platform versions for review. The final submit action and storefront scope remain Account Holder decisions.

    Reviewer environment¶

    App Review needs a reproducible path that does not depend on a private home network, short-lived token, personal media library, VPN, or reviewer-created server. Prefer a dedicated review account and a small non-personal library whose media and artwork are licensed for this use. The environment must support the same backend choice and core browse/play journey documented in the review notes and remain available throughout review.

    A public Jellyfin demonstration service may be evaluated as a candidate, but it is not automatically an acceptable dependency: confirm the operator permits App Review use, credentials are stable, Apple networks can reach it, and the sample library exercises the submitted clients. If any of those conditions is uncertain, run a dedicated review-only Jellyfin instance instead. Keep its credentials only in App Store Connect. Test the final instructions from clean installs on Vision Pro, iPhone, iPad, Apple TV, and Mac before submission.

    The reviewer and screenshot lane is the Labstream-controlled Jellyfin review catalog chosen in the licensed-media capture plan (#280). The 2026-08-22 evaluation of the official stable public demo established compatibility only; Labstream supports its passwordless Jellyfin login as of issue #283. It was not adopted because its shared account is mutable, downloads are disabled, service resets can interrupt sessions, and permission for third-party App Store marketing screenshots is unverified.

    Prefer a Labstream-controlled review instance with a deterministic catalog of original, public-domain, or appropriately Creative Commons media. Record every title, artwork source, license, attribution requirement, and permitted screenshot/review use in a repository manifest; do not use commercial movie or television artwork merely because a metadata provider can return it. The same catalog should drive automated screenshots and the reviewer journey so the captured UI matches the environment Apple can actually test.

    Public-release closeout¶

    After approval, verify the live product page and its support/privacy links, publish the exact corresponding source and release notes, create the authorized annotated tag, and record the released platform/version in this page. Do not describe an internal TestFlight build as a public App Store release.

    After launch: monitoring¶

    scripts/asc-digest.py is a read-only daily digest for the maintainer: new customer reviews (with platform where App Store Connect attributes it), Xcode Organizer diagnostic signatures (hangs, disk writes, launches) for the newest builds of the current marketing version on each platform, and TestFlight crash and screenshot feedback. It reuses the testflight-release.py credentials, issues only GET requests, and writes digest.md/digest.json to the gitignored artifacts/asc-digest/<date>/; stdout carries counts only. A state file there limits each run to items not seen before (--all ignores it; --since 7d widens the window). --logs and --attachments save diagnostic/crash logs and feedback screenshots to the same private directory. Review text, nicknames, tester emails, and logs are personal data: never paste them into issues, commits, or public docs. Endpoints that return 403/404 (common before the app is public) are listed as unavailable rather than failing the run. See Scripts.
