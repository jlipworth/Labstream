# 07 — Plex Official API Surface & Long-Term Stability

> **Archived research snapshot:** retained as dated evidence, not current architecture, feature
> status, or implementation guidance. Verify any reusable detail against the active docs and
> current source; old product assumptions, API versions, issue links, and paths may have drifted.

**Research date:** 2026-06-08
**Scope:** Official vs reverse-engineered Plex API surface for a personal-use visionOS Plex client. Goes beyond prior research (PIN-OAuth → `X-Plex-Token`, archived `plexswift`, rumored JWT migration) to characterize the *official* spec, the documented-vs-undocumented boundary, the cloud v2 API, and the auth-migration risk.

> **Convention used below:** "Official" = published by Plex Inc. on `plex.tv` / `developer.plex.tv` / `support.plex.tv` / `forums.plex.tv` staff posts. "Community" = third-party reverse-engineering (LukeHagar spec, Plexopedia, python-plexapi, forum devs). Uncertainty is flagged inline.

---

## TL;DR

- **Yes, an official OpenAPI spec now exists.** As of **Plex Pro Week '25 (announced 2025-09-29)**, Plex published a real, Plex-Inc-owned developer portal at **`developer.plex.tv/pms/`** with a Redoc-rendered OpenAPI document (currently **API version 1.2.2**, requires **PMS ≥ 1.43.2**). It is the first official PMS API documentation in Plex's history. ([blog](https://www.plex.tv/blog/plex-pro-week-25-api-unlocked/), [announcement](https://forums.plex.tv/t/public-api-docs-for-pms-are-here/930957), [portal](https://developer.plex.tv/pms/))
- **It is NOT the LukeHagar spec.** The official `developer.plex.tv` spec is a *separate, Plex-owned* artifact. The community `github.com/LukeHagar/plex-api-spec` (→ `plexswift`/`plexjs`/etc., generated by Speakeasy) is still community-maintained and unaffiliated; Plex's announcement never credits or adopts it.
- **The official spec covers transcoding/streaming**, not just metadata — it explicitly includes a Transcoder section ("Start a Transcoding Session", "Make a decision on media playback"). This is a real improvement over the DASH-only `plexswift`.
- **Auth in the official PMS spec is still legacy `X-Plex-Token`.** JWT is documented *separately* (forum/dev-corner, not yet in the PMS Redoc) and is **additive, not yet a deprecation**. As of **June 2026, `X-Plex-Token` still works and PMS only understands legacy tokens** — this is the central risk and the migration is mid-flight and under-documented.

## 1. Is there an official Plex OpenAPI specification?

**Two distinct specs exist. Do not conflate them.**

### 1a. Official: `developer.plex.tv/pms/` (Plex Inc.)
- Launched as part of **"Plex Pro Week '25: API Unlocked," blog dated 2025-09-29** ([plex.tv/blog](https://www.plex.tv/blog/plex-pro-week-25-api-unlocked/)) and announced on the forums ([forums.plex.tv/t/public-api-docs-for-pms-are-here/930957](https://forums.plex.tv/t/public-api-docs-for-pms-are-here/930957)).
- Rendered with **Redocly/Redoc**; the page exposes a **"Download OpenAPI specification"** link, so a machine-readable doc is available. ([developer.plex.tv/pms/](https://developer.plex.tv/pms/))
- **Version 1.2.2**, stated to be supported in **PMS ≥ 1.43.2**.
- Plex's own framing: it ends "years of developers having to reverse-engineer endpoints or rely on scattered community knowledge," but is explicitly **"not a complete 100% mirror of everything PMS can do just yet… a solid foundation — and one we plan to keep growing."** ([announcement](https://forums.plex.tv/t/public-api-docs-for-pms-are-here/930957))
- **Maintainer:** Plex Inc. **Completeness:** partial-but-substantial; admits gaps. **Last updated:** actively (v1.2.2 line tracks recent PMS builds).
- **Coverage — includes transcode/streaming, not metadata-only.** Documented sections include: General (server info/identity/library), Library Playlists, Library Collections, Status (sessions/history), Activities, Updater, Butler, Events (EventSource + WebSocket), Log, Preferences, Download Queue, UltraBlur, **Transcoder** (incl. "Start a Transcoding Session", subtitle/image transcoding, **"Make a decision on media playback"** = the transcode decision endpoint), Media Provider, DVR, Live TV. ([developer.plex.tv/pms/](https://developer.plex.tv/pms/))

> **Stability caveat (important for a long-lived client):** A developer raised that the downloadable spec sits at an **"unstable URL likely to change at any time"** (a blob-style path) and asked Plex for a permanent, versioned URL like Jellyfin's. **No Plex staff commitment to a stable/versioned URL was visible in the thread** as of this research. ([forums.plex.tv/t/request-stable-and-versioned-api-url/939305](https://forums.plex.tv/t/request-stable-and-versioned-api-url/939305)) → Treat the *download URL* as fragile even though the *portal* is official.

### 1b. Community: `github.com/LukeHagar/plex-api-spec`
- Description: "A Plex Media Server OpenAPI Specification **maintained by the community**." **Not** Plex-affiliated; no Plex endorsement in README or in Plex's announcement.
- **Verified via GitHub API (2026-06-08):** repo is **NOT archived**, `pushed_at` **2026-06-08** (actively maintained), ~81 stars. ([github.com/LukeHagar/plex-api-spec](https://github.com/LukeHagar/plex-api-spec))
- Generates 8 SDKs via **Speakeasy**: Python (`plexpy`/`plex-api-client`), JS/TS (`plexjs`), Go (`plexgo`), Ruby (`plexruby`), **Swift (`plexswift`)**, PHP (`plexphp`), Java (`plexjava`), C# (`plexcsharp`). Docs at `plexapi.dev`. SDKs are "automatically generated and may not be fully tested." ([README](https://github.com/LukeHagar/plex-api-spec))
- **`plexswift` is confirmed archived.** GitHub API: `archived: true`, last `updated_at` **2026-03-30**, last `pushed_at` 2025-10-12 ([github.com/LukeHagar/plexswift](https://github.com/LukeHagar/plexswift)). This matches the prior-research note ("archived Mar 2026"). The *spec* lives on; only the Swift SDK output was retired. Prior research's "DASH-only, no bitrate param" limitation is a property of that generated SDK, **not** of the official `developer.plex.tv` Transcoder section.

> **Verdict on usability:** The official spec is *usable as a reference* and is the better source for transcode/streaming today. But (a) there is **no official Swift SDK** — you'll hand-roll your networking layer regardless, and (b) the downloadable spec URL is not guaranteed stable. The community LukeHagar spec remains a useful cross-reference (it often documents query params the official Redoc glosses), but its Swift output (`plexswift`) is dead.

## 2. Officially documented vs reverse-engineered surface

| Client function | Endpoint family | Status |
|---|---|---|
| **Auth — PIN/OAuth (legacy)** | `plex.tv` / `clients.plex.tv` `/api/v2/pins`, `/auth`, `plex.tv/link` | **Officially documented** now (dev portal + support article). |
| **Auth — JWT / device-key** | `clients.plex.tv/api/v2/pins/<id>?deviceJWT=…`, JWK registration | **Semi-official / in-flight.** Documented in dev-corner + staff forum posts, **not** in the PMS Redoc yet. Incomplete. |
| **Browse / library / metadata** | PMS `/library/...`, `/library/sections`, `/search` | **Officially documented** (General + Media Provider sections). |
| **Transcode decision / start** | PMS `/video/:/transcode/universal/...`, decision endpoint | **Officially documented** (Transcoder section), though exact query-param coverage is thinner than community lore. |
| **Direct play / streaming** | PMS `/library/parts/...` with `X-Plex-Token` | Officially supported via token auth; specific URL construction still leans on community knowledge. |
| **Sessions / playback state / timeline** | PMS `/status/sessions`, `/:/timeline` | `/status/sessions` documented (Status). **Timeline is now officially documented** as "Report media timeline"; reference clients still show legacy GET forms/cadence details, so live-test method compatibility. |
| **Server discovery / per-server token** | `plex.tv` & `clients.plex.tv` `/api/v2/resources` | **Reverse-engineered / community-documented** (Plexopedia, python-plexapi). Widely used, not in the PMS spec (it's a cloud endpoint, not a PMS endpoint). |
| **Discover / Watchlist** | `discover.provider.plex.tv`, `community.plex.tv/api` (GraphQL) | **Reverse-engineered**, and **volatile** — Plex deprecated `metadata.provider.plex.tv` in favor of `discover.provider.plex.tv`, breaking community tools. ([support: Universal Watchlist](https://support.plex.tv/articles/universal-watchlist/)) |
| **Sync / Download Queue** | PMS Download Queue section | Partially documented (Download Queue); mobile "Sync" historically reverse-engineered. |

**Bottom line:** For a visionOS client, **auth + browse + transcode + playback-state plumbing now rest substantially on official docs** (a genuine change from the pre-2025 reverse-engineering era). **Server discovery (`/api/v2/resources`) and Discover/Watchlist remain reverse-engineered cloud endpoints** — usable but unstable, and Watchlist/Discover have *already* broken once via host migration.

## 3. plex.tv Cloud API v2 (`plex.tv` / `clients.plex.tv`)

Base hosts: **`https://plex.tv`** and **`https://clients.plex.tv`** (the latter is the newer canonical host for v2; both resolve for many endpoints). These are *cloud* endpoints, distinct from a PMS instance.

| Endpoint | Host | Method | Purpose | Token needed |
|---|---|---|---|---|
| `/api/v2/pins` | `clients.plex.tv` | POST | Create auth PIN (returns `id` + `code`); strong-PIN variant accepts a device JWK for JWT flow. | None to create; `X-Plex-Client-Identifier` required. |
| `/api/v2/pins/<id>` | `clients.plex.tv` | GET | Poll PIN; returns `authToken` once user authorizes (or, in JWT flow, exchange with `?deviceJWT=`). | None / device JWT. |
| `/api/v2/resources?includeHttps=1&includeRelay=1` | `plex.tv` / `clients.plex.tv` | GET | **Server/client discovery.** Returns each owned/shared PMS as a `Device` with `Connection[]` (local/remote/relay URIs) **and a per-server `accessToken`**. This is how a client finds servers + obtains the server-scoped token. | **Account token** (the user's `X-Plex-Token`). |
| `/api/v2/user` | `plex.tv` | GET | Account profile, subscription, settings. | Account token. |
| Watchlist | `discover.provider.plex.tv` (formerly `metadata.provider.plex.tv`) | GET | Universal Watchlist read/add/remove. | Account token. |
| Discover/community mutations | `community.plex.tv/api` | POST (GraphQL) | Ratings, privacy, watch-state settings. | Account token. |

**Token model — critical nuance:** the **account token** (from PIN flow) is used against *cloud* hosts. To talk to a **PMS**, you call `/api/v2/resources` with the account token, read the **per-server `accessToken`** from the matching `Device`, and use *that* as `X-Plex-Token` against the server's connection URI. ([Plexopedia: resources](https://www.plexopedia.com/plex-media-server/api-plextv/resources/), [python-plexapi myplex](https://python-plexapi.readthedocs.io/en/latest/modules/myplex.html))

## 4. Auth migration: static `X-Plex-Token` → JWT (THE KEY RISK)

### What's confirmed
- Plex **is** introducing **JWT auth**: public-key model where a device uploads a **JWK**, then requests **short-lived JWTs**, refreshing roughly **every 7 days**; a JWT can be exchanged for a Plex token also valid ~7 days. ([blog](https://www.plex.tv/blog/plex-pro-week-25-api-unlocked/), [forums JWT thread](https://forums.plex.tv/t/jwt-authentication/931646))
- Two onboarding paths: (1) **PIN flow** (recommended for new apps; `plex.tv/link` for 4-digit code) including the device's JWK to mint a JWT **without ever holding a legacy token**; (2) device-key registration + refresh. ([forums JWT thread](https://forums.plex.tv/t/jwt-authentication/931646), staff *marcelopazzo*, ~2025-10-01)
- Backward-compat intent: once you have a JWT, **"you can use it exactly like the old tokens in the `X-Plex-Token` header."** ([forums JWT thread](https://forums.plex.tv/t/jwt-authentication/931646))

### What's broken / uncertain right now (June 2026)
- **PMS does not understand JWTs.** Multiple devs report: `clients.plex.tv/api/v2/resources` called with a JWT returns **JWT** per-server tokens, which the **PMS then rejects with 401** — because "PMS does not understand JWT tokens: it only supports legacy tokens." ([forums.plex.tv/t/question-on-…-resources-and-jwt-authentication/934478](https://forums.plex.tv/t/question-on-https-clients-plex-tv-api-v2-resources-and-jwt-authentication/934478))
- The PIN→JWT exchange itself is reported flaky: a dev (SwiftPanda16) gets **no Plex JWT in the pin response** after sign-in. ([forums JWT thread #21](https://forums.plex.tv/t/jwt-authentication/931646/21))
- The **PMS Redoc (`developer.plex.tv/pms/`) still documents only `X-Plex-Token`** — "tokens are obtained from plex.tv." JWT is **absent from the official PMS spec**; it lives only in dev-corner/forum posts. The official **support article on finding `X-Plex-Token` is still live and unannotated** (no deprecation banner). ([support article](https://support.plex.tv/articles/204059436-finding-an-authentication-token-x-plex-token/))
- A former Plex dev (gbooker02) noted **direct client JWK registration "was not yet part of this system"** when last seen → the new-app path is still maturing. ([forums JWT thread](https://forums.plex.tv/t/jwt-authentication/931646))

### Timeline & verdict (flagged as uncertain)
- **No published deprecation date for `X-Plex-Token` exists.** I found none on plex.tv, support, or staff posts. Any specific date would be invented — do not assume one.
- **As of June 2026, `X-Plex-Token` still works and is the *only* thing PMS accepts.** JWT is currently an **additive cloud-auth layer**, not a replacement, and the PMS bridge is incomplete.
- **Risk verdict: MEDIUM, and architectural-not-imminent.** The static token is not going away tomorrow (PMS literally can't function without it yet), but the direction of travel is clear. **Concrete plan for the visionOS client:**
  1. Implement PIN/OAuth → token now (works, official, documented).
  2. **Abstract the auth/token layer behind one interface** so the credential source (static token vs JWT-exchanged token) can swap without touching networking.
  3. Generate and persist a **device JWK + stable `X-Plex-Client-Identifier`** from day one, so you can opt into the JWT/strong-PIN flow when it stabilizes without re-onboarding users.
  4. Plan to **store the per-server token from `/api/v2/resources` and treat it as refreshable** (assume ~7-day lifetimes are coming) rather than caching one token forever.
  5. Watch `forums.plex.tv/c/dev-community/113` for the deprecation announcement; that's where it will land first.

## 5. Rate limits, versioning conventions, and ToS

### Headers / content negotiation (official, from `developer.plex.tv/pms/`)
- Auth via `X-Plex-Token` header **or** query param. Common `X-Plex-*` headers: `X-Plex-Token`, `X-Plex-Client-Identifier` (stable per install — important), `X-Plex-Product`, `X-Plex-Version`, `X-Plex-Platform`, `X-Plex-Device-Name`. All can be sent as headers **or** query string.
- **Content negotiation:** responses are **XML by default**; **JSON only if you send `Accept: application/json`**. Official guidance: **"New applications should use JSON."** ([developer.plex.tv/pms/](https://developer.plex.tv/pms/))
- **Versioning:** the spec is version-stamped (1.2.2 ↔ PMS ≥ 1.43.2). There is **no path-based version segment** and **no committed-stable spec URL** yet (see §1a caveat). Cloud API uses an explicit `/api/v2/` prefix.

### Rate limits
- **No published numeric rate-limit policy.** Plex does not document client request limits.
- **`429 "API rate limit exceeded"` is real but mostly applies to plex.tv *infrastructure* endpoints** — certificate issuance, remote-access setup, user-sync — not normal library browsing. Multiple forum reports show 429s during cert/remote-access churn and bulk user-sync (e.g., Ombi). ([forums 429](https://forums.plex.tv/t/api-rate-limit-exceeded-429-new-server-setup-certificate-reset-request/935480), [Ombi #5003](https://github.com/Ombi-app/Ombi/issues/5003)) → **Mitigation:** back off on `/api/v2/resources` and cert/relay calls; cache discovery results; don't poll plex.tv tightly.

### Terms of Service (official: [plex.tv/about/privacy-legal/plex-terms-of-service](https://www.plex.tv/about/privacy-legal/plex-terms-of-service/))
- Plex's ToS defines **"Interfacing Software"** = software that accesses/calls PMS (plug-ins, agents, **client applications** communicating with the Plex Solution). Plex disclaims responsibility for your Interfacing Software and isn't obligated to support it — i.e., **third-party clients are contemplated and tolerated, not endorsed or supported.**
- **Anti-reverse-engineering clause:** you "shall not directly or indirectly disassemble, decompile, reverse-engineer, or… discover any source code, algorithms, trade secrets…underlying the Plex Solution." (Relevant given how much community knowledge *was* reverse-engineered — but note Plex has now *published* much of this surface officially, reducing exposure for a client that sticks to documented endpoints.)
- **No sublicense/redistribution/service-bureau use**, and **no "benefit of any third party."** → A **personal-use** visionOS client for your own account is squarely within normal use; redistribution-for-others or commercial multi-tenant use is where the ToS bites.
- The dev announcement reinforces this posture: Plex is **"not planning on vetting or giving official 'Stamps of Approval' on developer-built tools."** ([announcement](https://forums.plex.tv/t/public-api-docs-for-pms-are-here/930957))

> ⚠️ **Source hygiene:** `plexdevelopment.net/tos` and `plex.rockwellautomation.com` / `plex.com` surfaced in searches are **unrelated companies** (a Discord-bot host and Rockwell's manufacturing-ERP "Plex," respectively). They are **not** Plex/media ToS — ignore them. The only authoritative ToS is `plex.tv/about/privacy-legal/`.
